# 規約の点検

## 1. 機械的に判定できるものはテストで済ませる

```bash
cd tests && npx playwright test source-rules
```

`console.log` の直書き / `setTimeout`・`setInterval` / トップレベルの `let` /
空の JSDoc / `vh` に `dvh` が併記されているか / `getAvoidanceVector()` が
`calculateDestination()` の外から呼ばれていないか、の6つを見る。
**ここは自分で grep しない。** 通ってから先へ進む。

## 2. 判断が要るものを差分に対して見る

```bash
git diff                      # 未コミットの変更
git diff master...HEAD        # 公開中のものとの差
```

差分に出ている範囲だけを対象にする。ファイル全体を読み直さない。

### JSDoc に「なぜ」が書かれているか

**「何をするか」だけの JSDoc は、書いていないのと同じ**（コードを読めば分かる）。
規約が求めているのは、コードを読んでも分からないこと。

- 悪い: `/** 敵の数を数える */`
- よい: `/** 配列には撃破・撤退済みの艦が残るため、表示や判定には必ずこれを通す */`

新しく足した関数・メソッドに、判断の理由が書かれているかを見る。

### バランス数値を混ぜていないか

**リファクタリングやスタイル変更のコミットに、ゲームバランスの数値変更を
混ぜてはいけない。** バランス調整は `balance:` の別コミットにする。

差分の中で数値リテラルが変わっていたら、それがバランスに効くものか確かめる。
効くのは主にこのあたり:

- 各クラスの `static SHIELD_MAX` / `SHIELD_RECOVERY_RATE` / `SPIRIT` / `WEAPON`
- `TIMING` / `QTY` / `SCORE` の各値
- `NEW_ENEMY_INTERVAL` / `NEW_FEDERATION_INTERVAL`
- 「純粋な計算」ブロックの `calcTurnPenalty()` / `calcShipLossPenalty()` /
  `calcMissionClearBonus()`

混ざっていたら、コミットを分けるよう促す。

### ログの発信者は担当どおりか

`setMsg()` の第1引数（`SPEAKER.*`）には担当が決まっている。
**迷ったら `conductor/product-guidelines.md` を読む。** 記憶で判断しない。

操舵手 / 戦術士官 / 機関部 / 通信士 / 副長 / 基地 / 司令部 / コンピュータ。

### 色が意味に沿っているか

色は装飾ではなく**意味**を持つ。シアン=自軍 / 黄=警告 / 赤=危険 / 緑=良好 /
オレンジ・マゼンタ=敵。`MSG_COLOR` と `DRAW_COLOR` の選び方が、
その場面の意味に合っているかを見る。

CSS では `:root` のカスタムプロパティ経由が原則。ただし**現状すでに
`:root` を通していない色が9つある**ため、これは新しく足す分についてだけ
守る（既存分の整理は別の作業）。

### CONSTANT_CASE が実行中に変わっていないか

`CONSTANT_CASE` は実行中に変化しない値のためのもの。`const` オブジェクトの
プロパティを実行時に書き換えていないか見る（`const` は再代入を防ぐだけで、
プロパティの書き換えは止めない）。

## 3. 変更の種類ごとに、追加で見るもの

| 変更 | 見るもの |
|---|---|
| 表示・CSS | `/layout-check`。モバイルの縦横を省略しない |
| 挙動を変えないはずの変更 | `node make-baseline.js <ref>` → `npx playwright test regression` |
| 不具合の修正 | **その不具合を検出できるテストを足し、修正前のコードで実際に失敗させたか** |
| 新しい艦種・振る舞い | `instanceof` で分岐していないか（基底クラスのメソッドを override する） |

## 4. 最後に

```bash
cd tests && npx playwright test
```

全件通してから報告する。落ちたものがあれば、出力をそのまま伝える。
