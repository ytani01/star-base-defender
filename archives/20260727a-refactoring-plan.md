# Starbase Defender — リファクタリング計画

対象: `index.html` 内 `<script>` のゲームロジック（JS）

## 方針

- **ファイル分割なし。単一 `index.html` 構成を維持。**
- **HTML構造・全ての `id`/`class`・CSS設計トークンは変更しない。**
- **数値バランス（ダメージ計算・士気・シールド回復率など）や判定結果は一切変えない。**
- 今回の観点は「回りくどい処理」「無駄な処理」の解消による可読性・保守性の向上。過去の計画は白紙に戻し、現在の `develop` ブランチのコード（`v0.3.13`、約2600行）を読み直して洗い出した。

---

## 1. 最優先: `console.log` を「常時発火」から「デバッグ時だけON」に整理

デバッグ用の `console.log` 自体は残す。問題は、現状すべてが常時有効な状態でベタ書きされており、**移動計算・NPCの思考ルーチンなど、1ターン/1フレームで何度も呼ばれる箇所**に埋め込まれているため、普段のプレイ時にもコンソールが埋め尽くされ、必要な時に必要なログだけを見る、ということができない点。

| 場所 | 内容 | 頻度 |
|---|---|---|
| `resolveMovement()` (956, 961行) | `currentBestMoveSq`, `minTargetDistSq` | 扇形探索の内側ループ、1回の移動判定で最大36回発火 |
| `getTargetVector()` (1028行) | `console.log(obj)` （連邦艦の追跡対象オブジェクト配列） | 連邦艦の移動計算のたびに毎回発火 |
| `attemptPlayerMove()` (2040, 2055, 2068行) | `distFromBase`, `actualDist`, `actualDist(2)` | プレイヤーが移動するたびに発火 |
| `execNPCAction()` (2176行) | NPCのシールド・士気状態 | NPC1体の行動決定のたびに発火 |
| `npcMove()` (2286行) | 士気回復ログ | 逃走中NPCの移動完了のたびに発火 |
| `finalizeEnemyTurn()` (2321, 2328行) | 士気上昇・連邦艦数ログ | 増援出現の判定のたびに発火 |
| `Weapon` コンストラクタ (669行) | 武器パラメータ | 艦の生成のたびに発火 |
| `NPCShip` コンストラクタ (1116行) | 初期士気 | NPCの生成のたびに発火 |
| `nextMission()` (2410, 2416行) | ボーナス・連邦艦数 | ステージクリアのたびに発火 |
| `gameOver()` (2441行) | ゲームオーバー理由 | ゲームオーバーのたびに発火 |

**対応方針:** `DEBUG` フラグ（デフォルト `false`）+ `debugLog(...)` ラッパーを導入し、上記の `console.log` 呼び出しをすべて `debugLog(...)` に置き換える。ログの内容・出力タイミングは変えず、「常時出力」を「`DEBUG = true` のときだけ出力」にするだけ。開発中に `DEBUG` を `true` にすればこれまで通りすべてのログが見られる。挙動（ゲーム自体の動き）には一切影響しないため、最もリスクの低い変更として最初に着手する。

## 2. 移動ロジックの回りくどさ

### 2-1. `attemptPlayerMove()` の二段階迂回処理

`attemptPlayerMove()` は次の順序で処理している。

1. まず `clampDest()`（単純な直線移動＋衝突停止）を呼ぶ
2. 結果が `actualDist < 10` （＝ほぼ動けていない＝スタック）なら、あらためて `resolveMovement()` を呼ぶ

しかし `resolveMovement()` 自体が内部で最初に `clampDest()` を呼び、それでダメなら扇形探索を行う設計になっている（916〜971行）。つまり「狭い判定→ダメなら広い判定」を `attemptPlayerMove()` と `resolveMovement()` の**2つの階層で二重に**行っている。

- 最初から `resolveMovement()` だけを呼べば同じ結果になるはずだが、挙動を変えないために現状維持されているだけの可能性が高い。
- 一本化できないか要検証（プレイヤー移動は意図的に回避ベクトルを使わない設計 — 後述の「注意点」参照 — なので、一本化してもその方針自体は変えない）。

### 2-2. `resolveMovement()` の総当たり扇形探索

`sign in [1, -1]` × `角度5°刻みで5°〜90°` の二重ループ（最大36通り）で `clampDest()` を呼び直し、迂回先を探している（916〜971行）。ロジック自体は動作要件（迂回先を探す）に対して妥当だが、

- ループ内で最良解を更新する条件分岐が複雑で読みにくい（`stuck` 判定、`moveDistSq` の早期 `break` 条件など）。
- 前述の console.log 除去後、処理自体の意図（何を探索しているか）にコメントを補うことで、無駄な行を増やさずに可読性を上げられる。
- ループ回数やステップ幅を変えると移動の挙動（＝数値バランス）が変わるため、**探索アルゴリズム自体は変更しない**。整理対象はコードの見通しのみ。

### 2-3. `getTargetVector()` への `FederationShip` 固有ロジックの混入

`NPCShip` の汎用メソッドであるはずの `getTargetVector()` の中に、`if (this instanceof FederationShip) {...}` という分岐で連邦艦専用の「基地・自機に引き寄せられる」ロジックが直接埋め込まれている（1023〜1051行）。

- 汎用メソッドの中に特定サブクラスの分岐が入っているのは責務が混ざっている状態。
- `FederationShip` 側にオーバーライドとして切り出す（または対象重み付けをサブクラスから注入できるようにする）ことで、`NPCShip.getTargetVector()` は汎用ロジックのみに戻せる。
- 挙動（引き寄せられる強さの数値）は変更しない。

## 3. 重複ロジックの共通化

### 3-1. 敵艦スポーン処理が3箇所に重複

`new EnemyShip(scene, p.x, p.y); gameObjs.addEnemy(...)` という同じ組み合わせが以下の3箇所にそのまま書かれている。

- `create()` の初期配置ループ（1739〜1743行）
- `EnemyShip.onInteract()` の撃破時の再出現（1428〜1430行）
- `finalizeEnemyTurn()` の増援出現（2314〜2316行）

連邦艦にはすでに `newFederationShip(scene, dist_min, dist_max)` という共通関数があるので、同様に `spawnEnemy(scene, dist_min, dist_max)` を新設し、3箇所を置き換える。

### 3-2. `gameObjs.enemies` の直接書き換え

`GameObjs` クラスには `removeEnemy()`/`addEnemy()` という専用メソッドがすでに存在するのに、一部の場所ではそれを使わず配列を直接 `filter` で書き換えている。

- `FederationShip.onAfterAttack()`（1484行）: `gameObjs.enemies = gameObjs.enemies.filter(e => e !== target);`
- `finalizeEnemyTurn()`（2296行）: `gameObjs.enemies = gameObjs.enemies.filter(e => e.active);`（こちらは「非アクティブなものを掃除する」処理なので用途が異なり、そのままでも良い可能性はあるが、統一するかは要検討）

少なくとも `FederationShip.onAfterAttack()` は `gameObjs.removeEnemy(target)` に置き換えるべき（同じ結果になる単純な書き換え）。

### 3-3. `updateStatus()` のゲージ更新の反復

「シールド or エネルギーの割合を計算 → 閾値で色を決定 → テキストDOM更新 → ゲージ幅・色DOM更新」という同じ5行パターンが、Ship Shield / Ship Energy / Base Shield の3セット分そのまま書かれている（2378〜2400行）。

`updateGaugeDisplay(valueElId, gaugeElId, value, max)` のような共通関数に切り出すことで、約15行を5行程度に圧縮できる。表示される数値・色・閾値は変えない。

### 3-4. 円と線分の交差判定ロジックの重複

`clampDest()`（移動の衝突停止判定、883〜902行）と `hasObstacleOnPath()`（LOS/経路判定、1851〜1868行）は、どちらも独立に「線分と円の交差」を判別式（二次方程式）で解く同じ数学的処理を実装している。共通の幾何ヘルパー関数（例: `raySphereIntersection(src, dst, obj)` のようなもの）に切り出せないか検討する。純粋な数式の抽出なのでリスクは低いが、優先度は低め。

## 5. 実施順序案

1. **セクション1**（console.log除去）— 挙動に一切影響しない最優先・最低リスクの変更。
2. **セクション4**（死んだコードの削除）— 同じく最低リスク。1と合わせて実施可能。
3. **セクション3**（重複の共通化: スポーン処理、`removeEnemy`統一、ゲージ更新、交差判定） — 影響範囲が限定的で、置き換え前後で結果が一致することを確認しやすい。
4. **セクション2**（移動ロジックの整理） — 一番デリケートな部分。動作確認を最も丁寧に行う。

## 6. 変更してはいけないもの（制約）

- DOM の `id`/`class`、CSS設計トークン。
- ダメージ計算・士気（spirit）増減・シールド回復率などの数値ロジック。
- プレイヤー移動が**意図的に**回避ベクトル（`getAvoidanceVector`）を使わない設計になっている点（NPCとの重複統合を理由に誤って追加しないこと）。
- 単一 `index.html` 構成（ファイル分割はしない）。

## 7. 各ステップ後の確認シナリオ（最低限）

- 通常移動・障害物回避
- 敵への攻撃（命中/射程外/障害物あり）
- 基地へのドッキング/解除
- 自機シールド回復操作
- 敵撃破 → 新規敵出現
- 増援出現（`NEW_ENEMY_INTERVAL` / `NEW_FEDERATION_INTERVAL`、連邦艦のドッキング判定含む）
- ミッションクリア → ハイスコア登録 → ハイスコア一覧からの続行
- ゲームオーバー（基地陥落/自機撃破/エネルギー切れ）
