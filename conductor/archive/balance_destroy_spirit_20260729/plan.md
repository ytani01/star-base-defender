# Implementation Plan: 撃破したその場で敵の士気を上げる

対象: `index.html`、`tests/`、`conductor/product.md`、`docs/TBD.md`。

**進め方:** [Workflow](../../workflow.md) に従う。着手時に `[ ]` → `[~]`、完了時に `[x]` + コミットハッシュ7桁。
`plan.md` の更新は別コミット（`conductor(plan): ...`）にする。
フェーズ完了時はユーザーの承認を得てからチェックポイントを作る。

**この Track はゲームバランスを変える。** 挙動を変える変更（`balance:`）と、
テストや文書は別のコミットに分ける。**リファクタリングを混ぜない。**

`regression` の突き合わせは「一致すること」ではなく
**「差が士気に由来するものだけであること」**を見る。

コミット種別: `test:`

先にテストを置くのは、士気が**画面に出ない値**で、
実装したつもりで効いていなくても気づけないため。

- [x] Task: 「敵を撃破すると、生存している敵の士気が上がる」テストを追加する。上げ幅は `EnemyShip.SPIRIT.STEP` と突き合わせ、数値を直接書かない 〔spec: 完了の定義〕 [9d66331]
- [x] Task: 「上限（`SPIRIT.MAX`）を超えない」テストを追加する。あらかじめ上限近くに置いてから撃破する [9d66331]
- [x] Task: 「撃破に伴う増援の士気は `SPIRIT.INIT` である」テストを追加する。上昇と増援の順序を固定するため 〔spec: 機能要件〕 [9d66331]
- [x] Task: 「連邦艦が撃破した場合も上がる」テストを追加する。前 Track の `describe`「撃破に伴う増援は撃った相手によらない」に置いた盤面を流用できる [9d66331]

  流用のため `clearFieldFor()` / `placeFederation()` をファイル直下へ移した。
  離して置く敵の位置は `AREA_R * 0.75` の内側に直した
  （外側だと増援と見分けがつかない）。

  **「敵が撤退したときは士気が下がる」は足していない。** 既存の
  「敵が宇宙域の外へ出ると撤退し、残った敵の士気が下がる」が確かめている。
- [x] Task: **実装前のコードで上記が実際に失敗することを確かめる。** 失敗の内容を plan に記録する [9d66331]

  **結果:** 4件が失敗。すべて「士気が上がっていない」ことによる。

  | テスト | 期待 | 実際 |
  |---|---|---|
  | 残った敵の士気が上がる | 配列が +STEP | もとの値のまま |
  | 増援は初期値の士気で現れる | 0.55 | 0.5 |
  | 上限を超えない | 0.7 | 0.675 |
  | 連邦艦の撃破でも上がる | 0.55 | 0.5 |

  前提のアサーションは4件とも通過している（撃破が起きた／増援が1隻出た／
  狙われた敵は逃走していない／連邦艦が撃破した）。
  テスト一式は 88 passed / 4 failed（追加した4件のみ）。

  **作りで気をつけた点:** 撃破された艦は配列から取り除かれ増援が末尾に
  足されるので、添字では追えない。中心からの距離で「もとからいた敵」と
  「増援」を分けている。上げ幅の比較はページ側から読んだ `SPIRIT.STEP` を
  使い、両辺を同じ演算にそろえてある（浮動小数の差が出ない）。

## Phase 2: 士気の上昇を実装する

コミット種別: `balance:`

- [x] Task: `EnemyShip.onDestroyed()` に士気の上昇を足す。`gameObjs.removeEnemy()` → 士気の上昇 → `spawnEnemy()` の順にする。**増援が上昇を受けないのはこの順序による**ので、理由をコメントに残す 〔spec: 機能要件〕 [96d2f05]
- [x] Task: 上昇のログを足す。発信者は**副長**（撤退の報告と同じ担当）。文面は一報告一文、色は `MSG_COLOR.WARN`（戦況が不利に動いたことの警告）〔product-guidelines: 発信者を必ず名乗らせる／文体のルール〕 [96d2f05]

  文面は「撃破により敵の士気が高まっています」。原因を一文に含めたのは、
  ログが**因果を伝える唯一の手がかり**になるため。用語は
  `conductor/product.md` に合わせて「戦意」ではなく「士気」を使った。

  `getActiveEnemyCount() > 0` の番人を付けた。最後の1隻を撃破したときに
  「敵の士気が高まっています」と言わないため。`onLeaveArea()` と同じ形。
- [x] Task: ログを `onDestroyed()` の中に置く。前 Track では「発信者と文面が経路ごとに違う」ためログを呼び出し側に置いたが、**士気の上昇は誰が撃っても同じ報告**になるので、ここは中に置くのが正しい。判断の理由をコメントに残す [96d2f05]

## Phase 3: バランスの変化を読む

コミット種別: なし（確認のみ。必要なら追加の `balance:`）

- [x] Task: `node make-baseline.js <この Track の前の SHA>` → `npx playwright test regression`。**一致しないのが正しい。** 差が士気とその波及（逃走の閾値・交戦距離）だけであることを読み、内容を plan に記録する

  **予想は外れ、一致した（2 passed）。** 理由は、決まった操作列が
  `TURNS = 8` で、そのあいだに**撃破が起きないから**。
  `playScriptedTurns()` は 接近→攻撃→回復→基地 の4手を繰り返すので
  攻撃は2回しかなく、敵のシールド 300 に届かない。

  前 Track と同じ結論になる。**今回の変更は決まった操作列では踏めない。**
  Phase 1 で足した4件が唯一の番人。
- [x] Task: 実際に遊んで手応えを確かめる。**撃破を重ねたときに敵がどれだけ粘るようになるか**（4回でも上限 0.7 に達し、シールド 30% まで戦い続ける）。強すぎる／弱すぎると感じたら、上げ幅の再検討をユーザーに諮る 〔spec: 決定事項 1〕

  遊んでの手応えはユーザーの手動確認に委ねる。代わりに、使い捨ての計測を
  ヘッドレスで回して数字にした（計測用のテストは確認後に削除した）。

  | 撃破回数 | 士気 | 逃走する残量 | 追い返すのに要るダメージ | 交戦距離 |
  |---|---|---|---|---|
  | 0 | 0.50 | 150 (50%) | 150 | 70.0 |
  | 1 | 0.55 | 135 (45%) | 165 | 63.0 |
  | 2 | 0.60 | 120 (40%) | 180 | 56.0 |
  | 3 | 0.65 | 105 (35%) | 195 | 49.0 |
  | 4 | 0.70 | 90 (30%) | 210 | 42.0 |

  **実測: 逃走に転じさせるまでに要した射撃が 2発 → 3発に増えた。**
  士気 0.5 では2発、0.55 以上では3発（自機の1撃は距離40で80）。
  **撃破1回で、もう1発よけいに要る。**

  **もうひとつの実測:** 逃走に入った敵への攻撃をやめると、**80ターン
  経っても宇宙域から出ていかない**（シールドと士気が回復して戻ってくる）。
  これは士気の上昇と無関係な既存の設計だが、
  「追い出しきる前に手を緩めると押し返される」が実際に成立していることの
  裏づけになった。撃破の罰が重くなるほど、この粘りが効いてくる。
- [x] Task: 交戦距離が縮む副作用を確かめる。士気が上がると敵は**近づいてから撃つ**ようになる。撃つまでの手数が増えて「弱くなった」ように見えないか、実際の動きで見る

  **弱くはならない。近づく分だけ1撃が重くなる。**

  | 撃破回数 | 士気 | 交戦距離 | 敵の1撃の威力 |
  |---|---|---|---|
  | 0 | 0.50 | 70.0 | 45 |
  | 2 | 0.60 | 56.0 | 54 |
  | 4 | 0.70 | 42.0 | 66 |

  上限まで上がると **1撃あたり +47%**。撃つまでに寄る手数は増えるが、
  そのぶん命中時の被害が大きい。**両方向とも「敵が強くなる」で一貫している。**
- [x] Task: 確認シナリオを全項目通しで実行する（モバイルの縦画面・横画面を含む）〔workflow: フェーズ完了時の確認〕

  自動テスト一式 93 passed（`_baseline.html` を置いた状態なので、
  通常は飛ばされる突き合わせも含めて全件走っている）。
  表示に関わるコードは触れていないため `/layout-check` は不要と判断した。
  〈人〉の項目はユーザーの手動確認に回す。

## 補足: この Track で気をつける点

- **撃破の入口はすでに1つにまとまっている。** 前 Track で
  `EnemyShip.onDestroyed()` に集約済みなので、経路ごとの取りこぼしは起きない。
  逆に言えば、**ここに書いたことは4経路すべてに効く。**
- **増援に上昇を掛けない順序**（`removeEnemy` → 士気 → `spawnEnemy`）は
  仕様である。並べ替えると挙動が変わるので、コメントとテストの両方で守る。
- **撤退の減少と対称であること**が上げ幅の根拠。`SPIRIT.STEP` を
  片方だけ変えると対称が崩れる。
- **士気は画面に出ない。** テストは `EnemyShip.SPIRIT.*` と突き合わせ、
  0.05 のような数値をテスト側に書かない（バランス調整のたびにテストが嘘になる）。
- 撃破の罰が3つ（増援・減点・士気）重なる。**強すぎないかは実際に遊んで見る**
  ほかなく、Phase 3 をとばさない。
