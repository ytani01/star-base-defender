# Track: シナリオテストの実行を速くする

93件で 3.6 分かかっているシナリオテストを短くする。
**ゲーム本体には触れず、設定（並列実行）と待ち方（演出の時計）だけを変える。**

- [Spec](./spec.md) — 何を実現するか、何をやらないか
- [Plan](./plan.md) — フェーズ分けしたタスクリスト（進捗の唯一の正）

## なぜやるか

[Workflow](../../workflow.md) は「変更したら自動テストを走らせる」を原則に
掲げているが、**3.6 分は原則を守りにくくする長さ**で、
部分実行で済ませたくなる誘惑が生まれる。取りこぼしはそこから起きる。

時間の行き先は3つ。

| | |
|---|---|
| 直列実行 | `workers: 1`。各テストは自分のページを開いており、状態を共有していないのに1本で回している |
| 演出の待ち | 1ターンあたり約1.3秒（`TURN_DELAY` 400ms + `ENEMY_DELAY_MAX` 500ms ほか） |
| 起動 | テストごとの `openGame()` |

## 決めたこと

| | |
|---|---|
| 踏み込むのは設定と待ち方まで | テストの統廃合はしない。落ちたときにどの画面サイズかが分かることを優先する |
| 数値目標は置かない | 安全にできる範囲で短縮し、数字に合わせて無理をしない |
| ゲーム本体は変えない | `TIMING` の値も含む。演出はプレイヤーに届くもの |

## 何より気をつけること

**速くしたことでテストが嘘をつくようになってはならない。**

高速化の失敗は静かに起きる。待ちが甘くなればテストは常に通るようになり、
「速くて何も見つけないテスト」ができあがる。**遅いテストより有害。**

そのため Phase 0 で先に
**「ゲーム本体をわざと壊したときに落ちるテストの集合」**を控え、
各段階でそれが変わらないことを確かめる。
`determinism` と `regression` は、演出を速めても盤面の推移が変わらないことの
証明として働く。
