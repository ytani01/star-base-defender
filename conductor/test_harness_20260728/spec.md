# Spec: 自動テストの導入

## 概要

`conductor/workflow.md` の[確認シナリオ](../workflow.md#確認シナリオ)を、可能な範囲で
自動化する。人が確かめるべきものだけを人に残し、それ以外は機械が毎回同じ精度で確かめる
状態にする。

技術方針は [Tech Stack](../tech-stack.md#テストと静的解析) に記録済み（2026-07-28 決定）。

## 背景

- 本書の作成時点で、品質の担保は手動確認シナリオが唯一のゲートだった。
- `refactor_guidelines_20260728` の Phase 6 で純粋な計算の切り出しが済み、
  Tech Stack が定めていた「テスト導入の条件」が満たされた。
- 同 Track の Phase 5・6 では、乱数を固定して変更前後の全状態を突き合わせる方法で
  リグレッションの有無を確かめており、手作業では届かない精度が出ることが分かっている。
  この方法を使い捨てにせず、繰り返し使える形にする。

## 機能要件

### 計算のテスト（`tests.html`、依存なし）

- ブラウザで開くだけで結果が出ること。テストフレームワークを使わない。
- `index.html` を読み込んで、その中の関数を呼ぶ。ゲーム本体には手を加えない。
- 対象は「純粋な計算」セクションの関数と `Weapon` の威力計算。
  - 線分と円の交差、射線の遮蔽判定
  - スコアの増減（ターン経過・艦の喪失・クリアボーナス）
  - 威力減衰、有効射程と最大射程
- 失敗した項目と、期待値・実際の値が画面に出ること。

### シナリオテスト（`tests/`、Playwright）

- 確認シナリオの各項目に対応するテストを持ち、どの項目を自動化したかが対応づく。
- 盤面を再現できること（乱数の固定）。
- 変更前後の `index.html` を突き合わせ、挙動が変わっていないことを確かめられること。
- コンソールのエラー・警告がないことを確かめること。
- 画面サイズを変えて、宇宙域の見切れとステータス欄の占有率を確かめること。

### 文書

- 確認シナリオの各項目に、自動化済みかどうかが分かる印を付ける。
- テストの動かし方を書く。

## 範囲外

- **リンタ・型チェックの導入。** Tech Stack のとおり見送る。
- **ゲーム本体の分割や `export` の追加。** 単一ファイル構成は変えない。
- **実機スマートフォンでの見え方・タップ感の自動化。** 人が確かめる。
- **効果音が実際に鳴っているかの検証。** コードの経路までは確かめるが、音は聴かない。
- **ブラウザ差異の検証。** Chromium 系1つで確かめる。
- **CI の構築。** 手元で走ればよい。必要になったら別 Track にする。
- **カバレッジの計測。**
